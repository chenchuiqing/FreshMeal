# 第 3 章 系统分析

本章依据需求分析结果，从角色与权限、功能需求、业务流程、数据需求和非功能需求五个方面对系统进行分析，明确系统边界与验收标准。

## 3.1 角色分析

系统涉及四类使用者：消费者浏览商品、下单支付并跟踪配送；配送员在任务大厅接单并完成取货与送达上报；商家管理员维护商品、干预订单状态并执行配送调度；超级管理员在商家管理员权限之上增加用户与账号管理。角色用例图如图 3-1 所示，各角色对功能的访问权限如表 3-1 所列。

## 3.2 功能需求分析

功能需求按三端划分，并按 P0（核心链路，必须实现）、P1（增强功能，优先实现）、P2（可选功能）三级划分优先级。划分原则是：任何中断即导致用户无法完成“浏览—下单—收餐”闭环的需求定为 P0；提升运营效率与用户体验的需求定为 P1；依赖外部资源或非核心场景的需求定为 P2。用户端围绕交易主线提出需求，覆盖注册登录、商品浏览与筛选、购物车、立即购买与结算、下单支付、订单跟踪与个人中心，并结合轻食领域特征要求热量筛选与预约配送时段，如表 3-2 所列。

## 3.3 业务流程分析

订单主流程如图 3-2 所示。用户浏览商品后可加入购物车，或在详情页以立即购买按当前规格与选项直接下单（不写入购物车），两种方式均进入结算预览，页面试算商品金额、运费、优惠与整单热量；提交订单时由服务端重新计价并校验库存，扣减总库存的同时按 FEFO 策略扣减批次库存。支付成功后订单进入待接单，商家接单、出餐后：立即配送单直接进入待配送，预约单先进入待配送时段并由定时任务到点激活。订单进入待配送即生成配送单，经系统派单、抢单或人工指派分配配送员，随后依次完成取货、配送、送达，订单转入已完成并由用户评价；支付失败或超时则由定时任务自动取消订单并按原批次回补库存。

![图 3-2 系统业务流程图](figures/fig-3-2.png)

订单状态机如图 3-3 所示，共定义 10 个状态：待支付、待接单、备餐中、待配送时段、待配送、配送中、已完成、退款中、已退款与已取消。状态之间只允许沿迁移表定义的方向流转，非法迁移一律拒绝并返回状态冲突错误，从而将状态判断从业务代码中收敛到统一入口。

![图 3-3 订单状态机 UML 图](figures/fig-3-3.png)

配送流程与订单状态联动，如图 3-4 所示。订单进入待配送后生成状态为待分配的配送单，经三种方式之一完成分配：系统按多因子评分自动派单、配送员在任务大厅抢单、管理员人工指派。配送员确认接单后到店取货，配送单进入取货中，订单同步为配送中；到达收货地址确认送达后，配送单置为已送达，订单同步完成，全过程节点写入配送轨迹表供用户端时间轴展示。

## 3.4 数据需求分析

数据需求围绕交易与履约主线，核心表及其关键字段如表 3-5 所列。完整表结构将在 4.3 节展开。

表 3-5 核心数据字典

| 表名 | 关键字段 | 说明 |
|---|---|---|
| t_user | username、password、total_amount | 用户账号、BCrypt 密码与累计消费 |
| t_product | price、stock、calories、version | 商品价格、总库存、热量与乐观锁版本 |
| t_product_batch | expire_date、stock、status | 批次效期、批次库存与临期状态 |
| t_order | order_no、status、pay_amount、receiver_address | 订单号、状态机、实付金额与地址快照 |
| t_order_item | product_name、price、calories | 商品名、成交价与热量的下单快照 |
| t_payment | pay_no、status、expire_time | 支付流水号、状态与超时时间 |
| t_delivery_order | delivery_no、status、assign_type | 配送单号、配送状态与派单方式 |
| t_delivery_man | online_status、max_order_num、rating | 在线状态、负载上限与评分 |
| t_delivery_area | base_fee、per_km_fee、free_threshold | 起步价、里程费与免运门槛 |
| t_order_status_log | from_status、to_status、operator_type | 状态流转留痕与操作方 |

数据设计遵循三项原则：一是历史数据快照，订单明细冗余商品名称、图片、成交价与热量，商品信息后续变更不得影响历史订单的对账与退款；二是状态流转留痕，订单与配送单的每次状态变更都写入日志表，支撑用户端进度时间轴与后台审计；三是软删除与审计字段，用户、商品、地址等实体使用删除标记而非物理删除，全部业务表统一记录创建与更新时间。

## 3.5 非功能需求分析

除功能需求外，系统需满足以下非功能要求：

（1）**性能**：常规数据量下商品列表与订单列表接口 P95 响应时间低于 500ms；十万订单量级下看板统计查询低于 2s，可通过索引优化达成。

（2）**安全**：密码使用 BCrypt 哈希存储；未登录访问受保护接口返回 401，越权访问返回 403；订单金额一律由服务端计算，忽略前端传入金额；防御 SQL 注入与 XSS 攻击。

（3）**可靠性**：支付回调幂等，重复回调不重复改状态、不重复扣库存；下单扣减库存处于同一事务边界；超时订单由定时任务兜底取消并回补库存。

（4）**可用性**：移动端在 375px 宽度下无横向滚动，加载中、空数据与错误状态均有明确反馈。

（5）**可维护性**：统一响应体与全局异常处理，状态值集中定义为枚举，禁止魔法数字。

（6）**可移植性**：数据库连接、服务端口与文件路径全部通过配置文件外置，部署环境无须修改源码。

## 3.6 本章小结

本章完成了系统的角色与权限划分，给出了三端功能需求清单，建立了订单主流程、订单状态机与配送流程三组业务流程模型，梳理了核心数据字典，并从性能、安全、可靠性、可用性、可维护性与可移植性六个维度明确了非功能需求，为后续系统设计提供了依据。
