# 第 4 章 系统设计

本章在需求分析的基础上给出系统的总体架构、功能模块、数据库、订单状态机、派单算法、运费规则与接口设计，作为系统实现的依据。

## 4.1 系统总体架构设计

系统采用客户端层、接入层、应用层与数据层的四层架构，如图 4-1 所示。客户端层包含用户端商城、管理后台与配送员端三个前端应用；接入层由 Nginx 承担静态资源服务与反向代理，Sa-Token 认证过滤器统一完成 JWT 校验与 RBAC 角色鉴权；应用层是基于 Spring Boot 的单体后端，内部分为控制器、服务、数据访问与定时任务四个部分；数据层由 MySQL 8 承担业务持久化、Redis 承担会话与缓存、本地文件系统存储商品图片。请求经 Nginx 转发与认证鉴权后进入控制器，由服务层完成业务与事务控制，再由数据访问层落库。

![图 4-1 系统总体架构图](figures/fig-4-1.png)

应用层内部遵循分层职责约定：控制器层只做参数校验与服务调用，不编写业务逻辑；服务层是状态机流转、事务边界与算法实现的所在地；数据访问层基于 MyBatis-Plus，单表操作使用通用方法，统计聚合编写 XML SQL；定时任务层运行支付超时取消与预约时段激活两个兜底任务。公共层横切各层，提供统一响应、全局异常、状态枚举与策略实现。后端工程的目录结构如图 4-2 所示，`strategy` 包封装运费规则与派单评分算法，`enums` 包集中定义订单、配送、支付状态，杜绝魔法数字。

![图 4-2 后端工程结构图](figures/fig-4-2.png)

## 4.2 功能模块划分

后端按业务域划分为六个模块：用户模块负责账号、地址、购物车、订单与售后；商品模块负责分类、商品、规格选项与图集；订单模块负责下单计价、支付回调与状态机流转；配送模块负责配送单、配送轨迹、派单算法与运费计算；商家模块负责后台账号、批次库存、看板与内容管理；公共模块提供统一响应、异常、枚举与工具。模块间通过服务层接口调用，订单模块在状态迁移钩子中调用库存与配送模块，形成清晰的依赖方向。

三端功能模块依据第 3 章的功能需求划分。用户端围绕交易主线组织为商品浏览、购物车、结算支付、订单管理与个人中心五个模块，其中热量筛选与预约配送时段为轻食场景的差异化功能。管理端组织为商品管理、订单管理、配送调度、批次库存、配送配置、数据看板与系统管理七个模块。配送员端组织为任务大厅、抢单履约、上下线管理与业绩统计四个模块。三级优先级落实为：P0 模块的接口与表结构完整实现，P1 模块随主链路完成，P2 模块预留扩展点。

## 4.4 订单状态机设计

订单状态由集中式迁移表管控，共定义 10 个状态与对应编码：待支付（0）、待接单（1）、备餐中（2）、待配送时段（3）、待配送（4）、配送中（5）、已完成（6）、退款中（7）、已退款（8）、已取消（9）。状态迁移图如图 4-4 所示，合法迁移如表 4-3 所列，业务代码不得分散判断状态值，一律经状态机入口流转。

![图 4-4 订单状态迁移图](figures/fig-4-4.png)

表 4-3 订单状态迁移表

| 当前状态 | 可迁移目标状态 | 触发方与说明 |
|---|---|---|
| 待支付 | 待接单、已取消 | 支付成功回调；用户取消或支付超时 |
| 待接单 | 备餐中、退款中、已取消 | 商家接单；售后退款；商家拒单 |
| 备餐中 | 待配送时段、待配送、退款中 | 预约单入时段或非预约单直接待配送；售后退款 |
| 待配送时段 | 待配送、退款中 | 定时任务到点激活；售后退款 |
| 待配送 | 配送中、退款中、已取消 | 派单取货；售后退款；管理员干预取消 |
| 配送中 | 已完成、退款中 | 配送员送达上报；售后退款 |
| 已完成 | 退款中 | 售后退款申请 |
| 退款中 | 已退款或回滚原状态 | 退款完成；退款驳回回滚 |
| 已退款、已取消 | —（终态） | 不可再迁移 |

状态机在一次事务内完成三件事：校验目标状态是否在迁移表中，非法迁移抛出 40904 状态冲突错误；以当前状态为条件更新订单主表并写入流转日志（源状态、目标状态、操作方与时间），支撑进度时间轴与审计；执行目标状态对应的副作用钩子。副作用与状态一一绑定：进入待支付时完成服务端计价与乐观锁扣库存、FEFO 扣批次库存；进入待接单时置支付流水为成功；进入待配送时生成配送单并触发派单算法；进入配送中时同步配送单状态；进入已完成时结算配送员收入并更新用户累计消费；进入已取消时按原批次回补库存、作废配送单并退款。副作用钩子使库存、支付、配送逻辑与状态流转强绑定，避免在业务入口散落。

## 4.5 配送调度算法设计

系统派单采用候选集筛选与多因子加权评分两阶段设计，流程如图 4-5 所示。第一阶段在 SQL 层筛选候选配送员：账号启用、在线且空闲，服务区域覆盖订单收货区域，且当前在途单量（已分配、取货中、配送中三种状态）小于负载上限 `max_order_num`。候选集为空时订单保留在待配送状态，等待配送员抢单或管理员指派 [26]。

![图 4-5 派单算法流程图](figures/fig-4-5.png)

第二阶段对候选者按三个因子归一化打分并加权求和：距离因子以 10km 为基准线性归一化，越近得分越高；负载因子以在途单量与负载上限之比取补，越空闲得分越高；评分因子取配送员历史评分折算百分制。权重分配如表 4-4 所列：距离权重 0.5 占主导，保证配送时效；负载权重 0.3 防止订单堆积到少数人；评分权重 0.2 兼顾服务质量。按综合得分降序取最高者，分配结果连同各因子得分写入派单日志表，保证调度过程可回溯。

表 4-4 派单算法因子权重表

| 因子 | 权重 | 归一化方式 | 设计含义 |
|---|---:|---|---|
| 距离 | 0.5 | max(0, 1 − d/10) | 就近分配，主导时效 |
| 负载 | 0.3 | 1 − 在途单量/上限 | 均衡负载，防堆积 |
| 评分 | 0.2 | rating/5 | 优选高服务质量 |

为验证多因子加权相对单一策略的效果，设计对比仿真实验：随机生成 500 个派单场景，每场景含 1 个订单与 8 名配送员，订单位于门店周边 0.5～4km，配送员分布于 5km 范围内，负载上限 3～6 单，评分 3.5～5.0；三种策略各在同批场景上独立分配，统计平均配送距离与分配后平均负载率，结果如表 4-5 所列。多因子策略的平均距离较最近距离策略增加 0.55km，但平均负载率从 39.8% 降至 13.2%，即以有限的时效代价换取显著的负载均衡，更贴合高峰运营目标；先来先服务策略在两项指标上均表现最差，印证了基于实时状态评分的必要性。

表 4-5 派单算法对比实验结果

| 分配策略 | 平均配送距离/km | P90 距离/km | 分配后平均负载率 |
|---|---:|---:|---:|
| 最近距离优先 | 1.53 | 2.78 | 39.8% |
| 先来先服务 | 3.42 | 6.08 | 37.5% |
| 多因子加权（本文） | 2.08 | 3.63 | 13.2% |

## 4.6 配送费计算规则设计

运费计算采用策略模式，定义 `FreightRule` 接口与默认实现，计算流程如图 4-6 所示。结算预览与提交订单两个入口调用同一实现，保证试算与实付一致。计算先用 Haversine 公式求门店到收货地址的直线距离，再按收货地址区县优先、城市其次匹配启用中的配送区域，匹配失败则结算报错拒绝下单。

![图 4-6 运费计算流程图](figures/fig-4-6.png)

计费规则由四部分叠加：起步价覆盖首公里；超出首公里的部分按每公里单价累加，公式为运费 = 起步价 + max(0, 距离 − 1) × 每公里单价；下单时间处于 22:00 至次日 06:00 时加收夜间附加费；商品金额达到免运门槛时运费置零，门槛配置为 0 表示不参与免运。全部参数存放于配送区域表，商家可在管理端配置，无须修改代码。计算结果保留两位小数，直线距离作为预估距离展示，不用于精确结算。

## 4.7 接口设计

前后端交互遵循统一约定。成功响应固定为 `{"code": 200, "message": "success", "data": ..., "timestamp": ...}` 结构，分页响应的 `data` 携带 `records`、`total`、`current`、`size`、`pages` 字段；错误码按段划分语义：400xx 表示参数与业务校验失败，401xx 表示未认证，403xx 表示越权，404xx 表示资源不存在，409xx 表示状态冲突（状态机非法迁移即返回 40904），500xx 表示服务内部异常，由全局异常处理器统一转换为响应体。

接口按三端划分路径前缀并配置差异化鉴权：`/api/shop/**` 公共接口免登录、交易接口要求用户登录；`/api/rider/**` 要求配送员角色；`/api/admin/**` 要求管理员角色，用户与账号管理进一步要求超级管理员。核心接口如表 4-6 所列，完整清单见系统设计文档。支付流程的接口协作时序如图 4-7 所示：用户发起支付后服务端创建支付流水并返回收银台参数，前端跳转模拟收银台，收银台回调通知服务端；服务端先以 `pay_no` 唯一约束与流水状态做幂等校验，再校验订单归属与状态，随后在同一事务内更新支付流水、经状态机将订单由待支付推进至待接单并写流转日志；重复回调因幂等校验直接返回成功而不重复改状态。

## 4.8 本章小结

本章完成了系统的总体架构与工程结构设计，给出了六大后端业务模块与三端功能模块的划分，设计了包含 31 张数据表的数据库方案并明确核心表结构与设计原则；以集中式迁移表与副作用钩子实现了订单状态机，以候选集筛选与三因子加权设计了派单算法并通过对比实验验证了其负载均衡效果，以策略模式实现了可配置的运费规则，最后约定了统一响应、错误码、鉴权前缀与核心接口，并给出支付幂等时序。
