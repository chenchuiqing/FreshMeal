# 开发计划与进度管理

> 时间窗口：1–2 个月（约 8 周 / 40 个有效工作日）
> 核心原则：**论文与开发并行，绝不"写完代码再补论文"**；**每周一个可演示的增量**

---

## 一、现实评估（先看清楚再排期）

| 维度 | 评估 |
|---|---|
| 任务总量 | 3 端 × 约 18 个核心功能 + 25 张表 + 约 80 个接口 + 论文 1.5 万字 |
| 关键路径 | 下单交易链路 → 订单状态机 → 配送单与派单 → 管理端订单干预 → 配送员端闭环 |
| **最大风险** | **三端全上导致每个端都做不深**，答辩时"能演示但没亮点" |
| **第二风险** | 论文详细设计章节（占 1/3 篇幅）需要系统成型后才能写透，但写作需要前置 |
| 缓解措施 | ① 前 2 周冻结设计（本文档即产出）；② 每周末必须有可演示增量；③ P1/P2 明确砍掉不心疼 |

### 范围裁剪决策表（按截止时间倒推）

> |---|---|---|

## 三、论文与开发的并行节奏

**关键认知**：论文不能等开发完再写，否则你会发现要重新学一遍代码才能写明白。

| 论文章节 | 什么时候写 | 依据 |
|---|---|---|
| 第 1 章 绪论 | 第 1–2 周（可先写） | 背景 + 国内外现状需要查文献，可提前做 |
| 第 2 章 技术 | 第 2 周（边用边写） | 边学边写最省力 |
| 第 3 章 需求分析 | **第 1 周就有本文档**，第 6 周转成论文语言 | `01-需求分析.md` |
| 第 4 章 系统设计 | **第 1 周就有本文档**，第 6 周补充 + 补图 | `02/03` 文档 + 真实代码 |
| 第 5 章 系统实现 | 第 6–7 周（需要真实截图） | 代码 + 截图 |
| 第 6 章 系统测试 | 第 7 周（需要真实测试结果） | 测试记录 |
| 第 7 章 总结 | 第 7 周 | — |

> **本周就要做的两件"不写代码"的事**：
> 1. **开题报告 / 任务书**（很多学校第 2 周要交）——直接用本套文档改写即可；
> 2. **文献检索**——先查 30 篇与"即时配送调度""订单状态管理""预制菜供应链"相关的文献存好，绪论和第 4 章都要引。文献检索是最容易被拖到最后一周然后来不及的事。

## 四、每周检查点（周日晚自查）

```
□ 本周里程碑是否达成？（M1/M2/M3...）
□ 代码能否正常启动？有没有 commit？
□ 本周新写的接口有没有自测过？
□ 论文对应章节是否同步推进？
□ 有没有超范围加需求？（默认答案：没有，砍掉）
□ 数据库有没有手动改过而没同步 init.sql？（最常见的大坑）
```

> **铁律**：所有数据库结构变更**必须**同步写回 `server/src/main/resources/db/init.sql`，否则答辩前重建数据库时会全部丢失。

## 六、Git 提交规范

```
feat(user): 新增用户注册登录接口
fix(order): 修复超时订单未回补库存的问题
docs(db): 补充 t_delivery_area 表字段注释
refactor(service): 抽取订单状态机到独立管理器
```

**建议提交节奏**：每天至少 1 次提交，每个功能模块完成时打 tag：

```
v0.1.0-设计冻结      v0.2.0-认证完成      v0.3.0-交易链路完成
v0.4.0-配送体系完成   v0.5.0-管理端完成    v1.0.0-论文答辩版
```

**答辩前必须做的事**：打一个 `v1.0.0-答辩版` tag 并 `git archive` 导出纯净源码包 —— 避免把 `node_modules`、`.idea`、`target` 交上去。
