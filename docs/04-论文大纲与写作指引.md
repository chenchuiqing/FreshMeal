## 二、各章写作要点

### 第 1 章 绪论

**1.1 背景与意义**——从"轻食消费线上化率"与"预制菜的效期/营养双重约束"切入，最后落到"中小商家缺数字化工具"这个痛点。**不要写成一堆空话，要有具体数据或现象。**

**1.2 国内外研究现状**——按三条线梳理，每条线都要有文献支撑：
1. 餐饮外卖/网上商城系统的研究现状（国内：美团、饿了么的技术演进；国外：DoorDash、Uber Eats 的调度研究）
2. 即时配送调度算法的研究现状（路径规划、时间窗、VRP 问题、启发式算法与机器学习派单）
3. 预制菜供应链与效期管理的研究现状（批次追踪、FEFO 先进先出出库）

> **写法模板**：*……现有研究多聚焦于 X，但较少关注 Y 领域特有的 Z 问题。本文针对 Y 场景，设计并实现了一套……*

**1.3 主要研究内容**——列 4 条，与第 4 章的创新点一一对应（见下节）。

**1.4 论文组织结构**——一段话说明每章讲什么。

---

### 第 2 章 相关技术介绍

每节按"是什么 → 核心特性 → 本项目为什么用它 → 用法示例"四段式写。**不要写成教科书摘抄**——每项技术都要能回答"我在哪用了它"。

重点：
- 2.1 Spring Boot：重点讲**自动配置原理**（`@SpringBootApplication` → `@EnableAutoConfiguration` → `spring.factories`/`AutoConfiguration.imports`）与** starters 机制**，这是最常被问的点。再讲条件注解 `@ConditionalOnMissingBean`。
- 2.2 MyBatis-Plus：讲它对 MyBatis 的增强点（BaseMapper、Wrapper、分页插件、乐观锁插件 `@Version`），配代码片段。
- 2.5 JWT：讲**为什么用 JWT 而不是 Session**（无状态、前后端分离、多端、可水平扩展），讲 JWT 的三段结构与**签名防篡改原理**，并说明"JWT 无法主动失效"的解决方案（本项目用 Redis 维护黑名单/版本号）。

### 第 4 章 系统设计（**论文的核心，篇幅最大**）

**4.1 总体架构**：三层架构图（表现层/业务层/数据层），说明各层职责与技术选型。给出技术选型对比表（为什么 Spring Boot 而非 Node/微服务）。

**4.3 数据库设计**：
- E-R 图（用 draw.io 画成规范 ER 图，不要直接截图 mermaid，答辩老师对排版有要求）
- 主要表结构说明表（列出 8-10 张核心表的字段说明）
- **必须写出 2-3 个设计决策的理由**（比如订单快照冗余的理由、逻辑删除的理由），这是"设计"二字的体现
- **追加一段 FEFO 批次出库的策略论证**：为什么预制菜场景不能只用 FIFO —— 先到期先出能降低临期报损，并对比两种策略在同一订单序列下的报损差异。这是"预制菜"区别于普通外卖的领域设计，答辩时讲出来很加分

**4.4 订单状态机设计**：
- 状态图（UML State Diagram）
- 状态迁移表
- 钩子（Hook）机制说明
- 附核心代码（`OrderStatusManager`）

**4.5 配送调度算法设计**（**最重要的创新点，务必写透**）：
- 问题描述与形式化定义（候选集、约束条件、优化目标）
- 算法总体流程图
- 三个因子的归一化处理与权重设置依据
- 复杂度分析：候选集查询 O(1)（索引），打分 O(n)，排序 O(n log n)，总复杂度 O(n log n)，n 为候选配送员数
- **实验对比**：构造两组订单，横向对比"随机派单"与"本文算法"的配送平均时长、配送员负载极差两项指标，用表格呈现
- 可附 `t_delivery_man_log` 中的真实打分数据作为佐证

**4.6 配送费计算规则设计**：规则公式化表达（数学式或伪代码），说明可配置化的意义。

**4.7 接口设计**：给统一响应格式定义、主要接口的 RESTful 设计表格、统一错误码表。

### 第 7 章 总结与展望

**7.1 工作总结**——用"完成了什么"来写，不要用"学到了什么"：
> 本文针对轻食预制菜线上订购配送场景，设计并实现了一套基于 Spring Boot 的管理系统。系统采用前后端分离架构与 JWT 无状态认证……在订单流转上引入双状态机集中管控……在配送调度上设计了距离、负载、评分三因子加权算法并通过对比实验验证了其对负载均衡的改善……

**7.2 不足与展望**——写 3 条真实的不足（这也是防守性问题）：
1. 支付环节为沙箱模拟，未接入真实支付与第三方配送 API
2. 派单算法为静态权重，未考虑动态路况与订单实时到达的时间序列特征
3. 推荐模块仅基于健康标签规则匹配，未使用协同过滤

展望：接入微信小程序与真实支付；引入强化学习做动态权重；引入 LBS 路径规划。

## 三、创新点（答辩时重点讲，论文中也要明确写出来）

> 建议在第 1 章 1.3"主要研究内容"和第 4 章开头各写一次，形成呼应。

1. **领域适配的建模设计**：针对轻食预制菜"营养属性 + 效期约束"的双重特性，在商品模型中引入热量/蛋白质/脂肪/碳水/钠的五元组营养属性与过敏原、储存方式、保质期字段，并配套批次表与效期预警，使系统区别于通用电商商城。

2. **订单与配送双状态机的集中管控**：将订单状态与配送状态的流转规则抽取为迁移表与钩子机制，实现状态变更的合法性校验、留痕审计与副作用解耦，规避了业务代码中状态判断散落导致的逻辑不一致。

3. **配置化的配送费规则引擎**：将起步价、里程费、免运费门槛、夜间附加费等要素数据化，支持后台动态配置，规则扩展无需修改代码。

4. **多因子加权配送调度算法及其可观测实现**：融合距离、负载、评分三因子构建候选集筛选与加权评分模型，并完整持久化候选集打分中间过程，使调度结果具备可解释性与可验证性。

## 五、写作与排版规范

- **格式**：学校模板为准。默认宋体小四，1.5 倍行距，段落首行缩进 2 字符；一级标题黑体三号，二级黑体四号，三级黑体小四加粗；代码用 Consolas 小五号；表格用三线表。
- **图**：每个图下方必须有图题"图 4-5 派单算法流程图"，正文引用"如图 4-5 所示"。图片分辨率 ≥ 300dpi。
- **查重**：绪论和国内外现状最容易重复，务必用自己的话改写。技术介绍部分通常不算重复（因为要匹配自己的实现）。
- **引用**：每个技术点、每条研究现状都要有引用标注 `[1]`、`[2]`，参考文献格式统一（GB/T 7714）。
- **论文与代码一致性**：论文里写的每一个表名、接口路径、类名，必须在代码里真实存在。老师很可能会对照看。

**最容易被问倒的三类问题，提前准备**：
1. "你这个支付是假的吧？" → 说明沙箱模拟是毕业设计约束，真实接入需企业资质；重点讲**支付时序的完整性与幂等设计**，这与真实支付流程一致。
2. "你的创新点在哪？" → 讲第 4.3/4.4/4.5/4.6 节的四个设计（领域建模与 FEFO 出库、订单与配送双状态机、运费规则引擎、多因子加权派单算法）。
3. "数据量这么小，能测出性能吗？" → 承认规模限制，同时说明已做的压测与索引优化，以及大数据量下的优化路径（Redis 缓存、分库分表、读写分离）。
